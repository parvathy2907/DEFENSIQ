Behavioral signature extraction is the process of identifying and structuring the malicious behaviors observed during dynamic malware analysis. In this project, Cuckoo Sandbox generates JSON analysis reports containing execution metadata and behavioral evidence. These reports are processed programmatically to retrieve triggered signatures and their relevant attributes.

The extracted information provides the input for subsequent MITRE ATT&CK technique mapping, defense mapping, signature impact quantification, and residual-severity estimation.

---

## Cuckoo Report Processing

Each analyzed malware sample produces a JSON analysis report that serves as the primary input for report processing. The report contains available execution metadata, sample identification information, virtual-machine details, platform information, runtime options, and an aggregated threat score.

The report-processing module reads these JSON files and extracts the fields required by the project. It also retrieves the triggered signatures and associated attributes used to characterize the observed malware behaviors.

The processing workflow consists of the following steps:

1. **Load the report:** Read the JSON report generated after sandbox analysis.
2. **Extract metadata:** Retrieve available timestamps, execution duration, sample identity, platform details, runtime options, and aggregated threat score.
3. **Retrieve triggered signatures:** Extract the signatures recorded by Cuckoo during the analysis.
4. **Extract signature attributes:** Obtain available information such as signature name, severity score, and mark count.
5. **Prepare structured records:** Organize the extracted information for subsequent attack characterization and defense evaluation.

:::note[Explicit Missing-Field Handling]
The processing module handles missing fields and incomplete reports explicitly. An absent field is recorded as missing; it is never read as evidence that a behavior did not occur.
:::

## Triggered Signatures

For a sample *h*, the parser produces the set of triggered signatures S<sub>h</sub> = \{σ<sub>1</sub>, …, σ<sub>N</sub>\}, together with the API, registry, file and network behaviour recorded in the report. Each σ<sub>k</sub> is then scored for impact and mapped to ATT&CK, mitigations and D3FEND in Stage II.

A triggered signature represents a behavioral pattern identified by Cuckoo during sample analysis. Each signature provides information about a particular activity or condition observed during execution.

The project retrieves the triggered signatures from the generated analysis reports and extracts their relevant attributes. These signatures provide the behavioral representation used in subsequent attack–defense analysis.

## APIs and Behavioral Evidence

Application programming interface (API) calls provide information about operations performed by a program during execution. When API information is available in the analysis report or associated signature logic, it can help explain why a behavioral signature was triggered.

The project extracts APIs, execution actions, and malicious behavioral indicators from Cuckoo reports as part of its behavior-analysis workflow. This information helps characterize the actions associated with a triggered signature.

For example, a signature that monitors memory allocation and protection operations can provide evidence of a process manipulating memory permissions. Such behavior may be relevant to unpacking or code-loading activity, although an observation alone does not establish malicious intent.

The extracted evidence is then used to associate the observed behavior with MITRE ATT&CK techniques. The mapping is based on the behavior and its supporting evidence, not on an API name or signature description alone.

:::note[Observation Boundary]
The exact APIs and behavioral fields available depend on the report and configured analysis components. The project does not assume that every signature contains a complete API sequence or all relevant execution arguments.
:::

## Signature Attributes

Each triggered signature is represented using the attributes available in the Cuckoo report and the project's signature-processing logic.

| Attribute | Description |
|:---|:---|
| **Signature ID** | Identifier of the signature, when available. |
| **Signature Name** | Name assigned to the triggered behavioral signature. |
| **Severity Score (V<sub>x</sub>)** | Cuckoo's own severity value for the signature. It is the input to MAGIC impact scoring and is not the same as the impact score A<sub>k</sub> or the IS bound used for residual severity. |
| **Mark Count** | Count of marked events or related signature metadata, where available. |
| **Associated APIs** | API names associated with the behavior, when available. |
| **Behavioral Evidence** | Relevant execution actions or indicators extracted from the report, where available. |

Signature ID, signature name, severity score, and mark count are documented attributes in the project's report-processing workflow. Associated APIs and behavioral evidence are included when available from the relevant reports or signature records.

These attributes can be represented using the following conceptual structure:

```text
Signature = {ID, Name, Severity Score, Mark Count, Associated Behavioral Evidence}
```

The structure describes the information retained during extraction. It does not introduce additional confidence scores or severity weights that have not been defined in the implementation.

## Structured Output

The output of the extraction stage is a structured representation of the analysis report and its triggered signatures. This allows the project to process multiple samples consistently and pass the extracted data to downstream components.

The structure below shows the fields of each extracted record.

```json
{
  "sample_metadata": {
    "sample_id": null,
    "category": null,
    "type": null,
    "analysis_timestamp": null,
    "execution_duration": null,
    "platform_information": null,
    "runtime_options": null,
    "aggregated_threat_score": null
  },
  "extracted_signatures": [
    {
      "signature_id": null,
      "signature_name": null,
      "severity_score": null,
      "mark_count": null,
      "associated_apis": [],
      "behavioral_evidence": []
    }
  ]
}
```

:::note[Schema Integrity]
The `null` values and empty arrays shown here are placeholders, not observations. Optional fields are filled only when the source report contains the corresponding information.

ATT&CK technique identifiers and defense mappings are added in later stages of the workflow; they are not extracted from the Cuckoo report.
:::

## Example Input and Output

### Input: Cuckoo Analysis Report

The input is the JSON report generated after analyzing a malware sample. It contains the metadata and execution information recorded by the configured sandbox.

The report-processing module reads the relevant fields and retrieves the triggered signatures and their attributes.

### Processing

The report is parsed to extract:

1. Sample and execution metadata.
2. Triggered signature records.
3. Signature names and identifiers.
4. Severity scores and mark counts, where available.
5. Associated API information and behavioral evidence, where available.

The extracted fields are organized into structured records suitable for downstream processing.

### Output: Structured Behavioral Records

The output contains the extracted sample metadata and triggered signatures. These records serve as the inputs for the project's attack characterization and impact-quantification stages.

A separate mapping stage associates the observed behavior with MITRE ATT&CK techniques and identifies candidate defensive mechanisms through the project's ATT&CK–D3FEND mapping process.

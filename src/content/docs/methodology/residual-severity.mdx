The Residual_Severity module estimates the remaining severity of a malware behavior when it is evaluated against a selected defensive technique. The estimate is supplied to the Cooperative Co-Evolutionary Algorithm (CCEA), which uses it when it scores candidate defense combinations.

---

## Two Modes: CSV and LLM

| Mode | Source of residual severity | Purpose |
|:---|:---|:---|
| **CSV mode** | Pre-computed RS table containing one result per signature–defense pair | Enables fast, deterministic and repeatable evaluation, allowing CCEA and random search to use an identical RS source |
| **LLM mode** | Locally executed MiST-8B model using structured attack and defense context | Estimates RS for individual signature–defense pairs and supports evaluation of model-generated assessments |

The operating mode is selected through a configuration toggle, and both modes expose a common RS interface to the CCEA. The optimizer does not change when the RS source changes.

---

## RS Value Used in This Work

Residual severity RS is an integer, and its scale depends on the mode.

| Mode | Scale of RS | Meaning of the ends | Values that occur | How RS enters the fitness |
|:---|:---|:---|:---|:---|
| **CSV mode** | Integer from 0 to RS<sub>max</sub> = 10 | 0 = nothing left; a larger value = less of the behavior is mitigated | 0 to 6 in our table | RM<sub>k</sub> = RS / RS<sub>max</sub> |
| **LLM mode** | Integer from 0 to V<sub>k</sub>, the original Cuckoo severity of the signature | 0 = nothing left; V<sub>k</sub> = the defense does not reduce the behavior | V<sub>k</sub> is 1 to 6 in our data; 1 to 4 for Sample02 | RM<sub>k</sub> = AM<sub>k</sub> · RS / V<sub>k</sub> |

In LLM mode the residual is anchored to the signature's normalized impact AM<sub>k</sub>, so no mitigation leaves RM<sub>k</sub> = AM<sub>k</sub> and full mitigation gives RM<sub>k</sub> = 0. A signature whose candidate defenses were all skipped (no D3FEND match) has no assessed candidate and keeps RM<sub>k</sub> = AM<sub>k</sub>. In both modes RM<sub>k</sub> lies in [0, 1]. The full fitness is on the [CCEA page](/methodology/ccea/).

:::note[Prediction vs. verified risk]
RS is an estimate of the severity that may remain after considering the defense. It is not a verified risk value, and a mapped defense is not assumed to mitigate an attack merely because the two are related in the ontology.
:::

## Inputs

Each input row represents one signature–defense assessment and contains:

- **Attack-side context:** the Cuckoo signature name or identifier; the original Cuckoo severity; the MITRE ATT&CK tactic and technique; the signature description and categories; the trigger type and a summary of the detection logic; and the available API filters, indicators and TTP metadata. Attack information is retrieved from the pre-generated `cuckoo_signatures.json` catalogue. Missing metadata is explicitly identified rather than inferred without supporting evidence.
- **Defense-side context:** the exact MITRE D3FEND defense name supplied in the input; the resolved D3FEND identifier and ontology URI; the official defense definition; the associated digital artifacts; defensive relationships such as `blocks`, `filters`, `restricts`, `analyzes`, `strengthens` and `hardens`, wherever available; and the provenance of each ontology relationship. Defense names are resolved against the D3FEND ontology using RDFLib and exact label matching. Unresolved or ambiguous defenses are marked and skipped rather than guessed.

---

## Execution Flow

Each run proceeds in seven steps:

1. **Input ingestion:** read the input table (with columns such as signature name, tactics, technique, defense and initial severity), validate the required columns, preserve a stable evaluation identifier for each row, and compute an input hash for reproducibility and resume checks.
2. **RDF graph construction:** use RDFLib to represent each assessment row and its links to the signature, ATT&CK tactic, ATT&CK technique, defense and initial severity.
3. **Cuckoo metadata retrieval:** look up the signature in `cuckoo_signatures.json` (generated from the original Cuckoo signature files) for its description, severity, categories, TTP metadata, monitored APIs, trigger type, detection summary, indicators and source file. The pipeline consumes this catalogue and does not parse or execute the original Python signatures.
4. **D3FEND ontology ingestion:** load the pinned D3FEND OWL/TTL ontology into an RDFLib graph and retrieve the defensive-technique labels and digital-artifact vocabulary.
5. **Defense resolution:** resolve the supplied defense name and, for a unique match, retrieve its identifier, URI, definition, associated artifacts and artifact relationships.
6. **Unified MiST-8B assessment:** combine the attack, ATT&CK and defense context with the initial severity in one prompt; a single inference call per resolvable row returns the artifact interpretation and the RS estimate together.
7. **Validation and storage:** parse and validate the response, attach the result to the RDF assessment, checkpoint the graph, and export a summary CSV of evaluated and skipped rows.

Each row is assessed on its own: the model considers only the defense in the current row and does not assume that the signature's other candidate defenses are deployed. The Cuckoo metadata is signature-derived behavioral evidence, not complete raw sandbox telemetry, and the original TTP metadata is not treated as an independently revalidated ATT&CK mapping.

---

## Defense Resolution Statuses

Every row receives one of five statuses:

| Status | Handling |
|:---|:---|
| `exact_match` | One ontology term matches the supplied label; context is retrieved and the row proceeds to inference |
| `normalized_match` | A match is found after permitted normalization (e.g. trimming whitespace); the status is recorded and the row proceeds |
| `ambiguous_match` | Several candidates match; the row and its candidates are preserved and inference is skipped pending resolution |
| `not_found_in_d3fend` | No match is found; the row is preserved and skipped, and no identifier or substitute defense is invented |
| `retrieval_error` | Ontology parsing or retrieval fails; the error is recorded and the row is not treated as matched |

A skipped row is not a model prediction: its RS remains null and it is excluded from prediction-accuracy metrics, with the number of skipped rows reported separately.

## MiST-8B Assessment

In LLM mode, the retrieved attack and defense contexts are combined into a single structured prompt and submitted to the local MiST-8B model (served by Ollama, GGUF Q4_K_M, 4-bit quantization). For each signature–defense pair, the model performs a unified assessment:

1. interprets the observed malware behavior using the Cuckoo signature metadata and ATT&CK context;
2. identifies the relevant attack artifacts and evaluates the defensive scope described by D3FEND;
3. assesses the relationship between the attack behavior and the selected defense;
4. identifies the behaviors addressed by the defense and the capabilities that may remain;
5. estimates the residual severity based on the available evidence.

The assessment follows six rules:

- estimate RS directly, without predefined numerical deductions for individual defense categories;
- do not assume that an artifact relationship guarantees mitigation;
- do not assume a defense is ineffective solely because the listed artifacts differ;
- do not invent defensive capabilities, deployment conditions or attack evidence;
- distinguish preventive, restrictive, detective and observational capabilities where the ontology supports it;
- explicitly flag uncertainty when the supplied evidence is insufficient.

## Output Schema

| Field | Type | Meaning |
|:---|:---|:---|
| `evaluation_id` | String | Unique identifier of the signature–defense assessment |
| `signature_name` | String | Cuckoo behavioral signature being evaluated |
| `defense_name` | String | Selected D3FEND defensive technique |
| `initial_severity` | Numeric | Original Cuckoo severity, preserved without MAGIC quantization |
| `residual_severity` | Integer | Estimated severity remaining after considering the selected defense: 0 (nothing left) to V<sub>k</sub>, the original Cuckoo severity of the signature |
| `mitigation_label` | Enum | `NONE`, `PARTIAL` or `FULL` |
| `covered_behaviors` | Array | Observed behaviors addressed by the defense |
| `remaining_attack_capability` | String | Capabilities that may remain after considering the defense |
| `justification` | String | Concise, evidence-based explanation for the RS estimate |
| `uncertainty_flag` | Boolean | Whether the supplied evidence is insufficient for a reliable assessment |

---

## Output Validation

Every MiST-8B response undergoes seven checks:

1. strict JSON parsing;
2. schema and data-type validation;
3. residual-severity numeric-type validation;
4. severity-range validation: 0 ≤ RS ≤ V<sub>k</sub> (LLM mode; 0 ≤ RS ≤ 10 in CSV mode);
5. mitigation-label validation against \{`NONE`, `PARTIAL`, `FULL`\};
6. provenance checks against the supplied attack and defense context;
7. logging of invalid outputs, local inference errors and failed correction attempts.

:::caution[No silent clamping]
Out-of-range values are never silently clamped. Invalid responses are logged and may undergo a controlled correction attempt. A structurally valid response does not establish empirical correctness, so RS estimates must be evaluated separately against reference assessments.
:::

---

## Scope of Claims

The module estimates RS from Cuckoo-derived behavioral evidence and D3FEND ontology context, resolves defense names against a specified ontology version, identifies ontology artifact relationships, and produces structured outputs that pass defined validation. It does not claim that a defense experimentally stops the malware, that artifact overlap alone proves mitigation, that every valid JSON response is correct, or that a D3FEND relationship guarantees real-world effectiveness. Real effectiveness also depends on deployment, configuration, coverage and environment.

---

## Experiment Logging and Reproducibility

Each LLM assessment records:

- the provider and runtime (local inference) and the model identifier (MiST-8B);
- the model quantization and runtime configuration, where available;
- the input representation and retrieved context, and the prompt version or hash;
- the temperature and sampling parameters, and the random seed where supported;
- the output schema and validation method;
- the timestamp, inference latency and token usage (where available);
- the response and validation status.

The RDF graph and summary CSV preserve the individual assessment results. Resume functionality prevents previously generated results from being reused when the run identity changes; that identity covers the input CSV hash, the Cuckoo JSON hash, the D3FEND ontology version or file hash, the MiST-8B identifier and quantization or runtime configuration, the prompt version or hash, the output-schema and validation version, and the inference parameters. Fields the local runtime does not expose are recorded as unavailable rather than estimated.

## Benchmark Metrics

The RS estimates are evaluated against independently labelled reference values. For *n* signature–defense pairs, let ŷ<sub>i</sub> be the predicted and y<sub>i</sub> the reference residual severity. Both are integers on the RS scale of this work: from 0 (nothing left) up to RS<sub>max</sub> = 10, the upper bound of the scale (in LLM mode the values stay at or below V<sub>k</sub> ≤ 6). All metrics use this one scale, so that results for different signatures can be pooled.

| Metric | Definition | Purpose |
|:---|:---|:---|
| **Quadratic Weighted Kappa (QWK)** | 1 − Σ w<sub>ij</sub>O<sub>ij</sub> / Σ w<sub>ij</sub>E<sub>ij</sub>, with w<sub>ij</sub> = (i − j)² / RS<sub>max</sub>² | Agreement on an ordinal scale; a large miss is penalized more than a near miss |
| **Normalized MAE** | (1/n) Σ \|ŷ<sub>i</sub> − y<sub>i</sub>\| / RS<sub>max</sub> | Each error as a share of the RS scale |
| **Exact-match accuracy** | (1/n) Σ [ŷ<sub>i</sub> = y<sub>i</sub>] | Share of exact predictions |
| **Accuracy@±1** | (1/n) Σ [\|ŷ<sub>i</sub> − y<sub>i</sub>\| ≤ 1] | Separates near-misses from real errors |
| **Macro-F1** | Mean F1 over FULL, PARTIAL and NONE | Quality of the mitigation labels |

Each run reports the numbers of eligible, skipped, invalid, failed and successful cases. Reference labelling is in progress, so these metrics have not yet been reported; see [Results](/evaluation/results/) for the Sample02 case study.

## Limitations

1. **Dependence on input evidence:** the model reasons only from the evidence supplied. Incomplete sandbox observations or incomplete defense mappings can lead to inaccurate estimates.
2. **Model and prompt sensitivity:** estimates may vary with the model version, quantization, prompt and inference parameters, which are therefore recorded.
3. **Assumptions about defenses:** the model may over- or underestimate a defense's effect. A related defense does not necessarily prevent the behavior.
4. **D3FEND coverage:** a defense name that does not resolve in D3FEND is skipped; in Sample02, 4 of 24 defense names did not resolve, leaving six signatures with no assessable candidate.
5. **Reference labels:** no reference labels exist yet, so QWK, MAE and macro-F1 cannot yet be reported.
6. **Limits of validation:** schema and range checks establish that a prediction is structurally valid, not that it reflects the real effectiveness of a defense.
